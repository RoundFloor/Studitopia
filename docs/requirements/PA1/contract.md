## 4. Work Schedule and Scrum Process

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

The team follows the Scrum process required by PA1. Each Sprint includes:

- **1 Sprint Planning meeting**
- **2 Scrum meetings**
- **1 Sprint Review meeting**

Meeting format follows the course **WeeklyReports** guidelines.

### Task Management

Every project-related task must be recorded, including coding, testing, documentation, research, and self-training tasks.

Each task:

- Is assigned to **exactly one** team member.
- Has a creation date, assignment date, and completion date.
- Is created and assigned **before work begins**.
- Is marked complete only when the work is actually finished.

### Deadlines and Delays

- Sprint tasks and expected outcomes are agreed during Sprint Planning.
- Members report blockers as soon as they are identified.
- A member who expects to miss a deadline must notify the team, explain the reason, provide a revised estimate, and help reduce the impact on dependent work.
- If necessary, the team reprioritizes or redistributes tasks.

## 5. Code, Git, Documentation, and Testing Standards

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

### Code

- Follow the conventions of the selected language and framework.
- Use clear names and keep modules/functions reasonably focused.
- Avoid unnecessary duplication.
- Keep code readable, maintainable, and testable.
- Never commit API keys, passwords, credentials, or other secrets.

### Git

- All source code and Markdown documentation are version-controlled.
- Use clear commit messages.
- Significant changes should be reviewed before merging.
- The repository remains private as required by PA1.

### Documentation

Documentation is maintained in Markdown and stored in the repository. It includes requirements, analysis/design, testing, management reports, and other required project documents.

Mermaid is used for diagrams whenever practical.

### Testing

Testing is a shared responsibility. The team performs appropriate component/unit, integration, system, and acceptance testing. A feature is considered complete only after its implementation has been reviewed and appropriately tested.

## 6. Accountability and Performance

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

Contribution is evaluated using evidence such as:

- Completed task-management items
- Git commits and pull requests
- Code reviews
- Testing and documentation
- Meeting participation
- Communication and timely reporting
- Quality and completeness of deliverables

Commit count alone is not a measure of contribution.

If a member repeatedly fails to participate or complete assigned work:

1. The team discusses the issue with the member.
2. The cause and corrective action are identified.
3. Tasks may be adjusted or reassigned to protect project progress.
4. The issue may be documented with supporting evidence.
5. Persistent problems may be escalated to the TA or instructor.

## 7. Decision-Making

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

The team uses the following process:

1. **Discussion:** Seek consensus based on requirements, user value, feasibility, cost, risks, and maintainability.
2. **Majority vote:** If consensus cannot be reached, each member has one vote and the majority decides.
3. **Escalation:** If a major disagreement remains unresolved, the team consults the TA or instructor.

The primary coordinator facilitates decisions but has no unilateral authority to override the team.

---

## 8. Conflict Resolution

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

The team resolves conflicts as follows:

1. Clearly identify the issue.
2. Allow each involved member to explain their position.
3. Separate facts, requirements, assumptions, and personal preferences.
4. Discuss possible solutions and consequences.
5. Reach consensus or use majority vote.
6. Record decisions that affect the project.
7. Escalate unresolved issues to the TA or instructor.

Personal attacks, harassment, deliberate exclusion, and withholding important project information are unacceptable.

## 9. AI-Assisted Development

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

The team may use AI coding tools as development aids in accordance with the requirements and policies officially specified by CS300.

Members must:

- Understand AI-assisted code before using it.
- Review and test AI-assisted output before integration.
- Validate important technical information rather than assuming AI output is correct.
- Protect API keys, credentials, private information, and other secrets.
- Remain responsible for all submitted code, documentation, and results.

AI assistance does not transfer responsibility for the resulting work from the team member to the AI tool.

## 10. Change and Risk Management

**Performed by:** [Tuan] | **Reviewed by:** [Name] | **Edited by:** [Name]

The team expects requirements and technical decisions to evolve during development.

Before making a significant change, the team considers:

- Reason and expected value
- Affected requirements and existing work
- Effort and dependencies
- Technical and project risks
- Impact on the current and future Sprint

Important changes are discussed before implementation. Risks and blockers are reported early so that the team can reduce rework and protect Sprint goals.
